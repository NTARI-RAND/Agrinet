# Agrinet account, federation and request-limit hardening

This branch closes the account-overwrite and unprotected federation paths and prepares the chat PRs to use the same distributed limit store.

## Account and user-response boundaries

- POST /users is administrative provisioning only. It requires a verified JWT principal whose role is admin; the browser/API-key path does not create req.user and cannot pass this check.
- IDs are generated by the server. A supplied id is rejected. DynamoDB writes use attribute_not_exists(id) so a collision cannot replace a prior account.
- Public /users responses are a narrow directory DTO. /api/admin/users requires an administrator and returns an administrative DTO, not a raw DynamoDB row.
- Login responses use the authenticated-account DTO. Password hashes, verification codes and exact coordinates are never included.
- Public signup remains /api/auth/register and uses a conditional create.

## Federation peer authentication

Federation endpoints are mounted before the general browser/API-key middleware and require HMAC peer authentication themselves. They do not accept the shared browser API key as peer identity.

Each peer pair needs a distinct random secret of at least 32 characters:

- FEDERATION_LOCAL_NODE_ID (or existing NODE_ID) is this node's stable identity.
- FEDERATION_OUTBOUND_PEERS_JSON maps each remote NodeRegistry.nodeId to the secret this node uses when contacting that peer.
- FEDERATION_PEERS_JSON maps authorized inbound sender node IDs to their matching shared secrets.

For A to synchronize with B, A's outbound entry for B must match B's inbound entry for A. The reverse direction can use a different secret. Never put these values in browser code or commit a real .env file. Keep node clocks synchronized; signed requests and responses have a five-minute clock-skew window.

Requests sign the timestamp, HTTP method, path and SHA-256 digest of the exact request body. Export responses are also signed and checked against the node ID in the local NodeRegistry record. Production peers must use HTTPS; HTTP is accepted only for loopback development.

Federation user imports accept an explicit user-field allowlist, reject existing IDs atomically, strip passwords, contact fields, roles and verification state, and record sourceNodeId from the authenticated peer plus remoteUserId. Claimed origin identifiers are retained as provenance metadata from the signed peer payload; they never determine the authenticated sender.

Exports use bounded cursor pages and explicit listing/transaction field allowlists; account records, local dialog narrative and scalar ratings are omitted. Scheduled federation paths verify signed pages and report inspection counts without importing or advancing lastSyncAt. Manual imports retain the source-bound security controls above. See collection-pagination.md for the complete inspection contract.

## Distributed request and connection limits

express-rate-limit is used for API, user writes, location, chat, stream and federation traffic. Chat routes require an account JWT (`chatAuth`); the shared browser/API key is explicitly rejected for private chat. Authenticated requests are keyed by req.user.userId; authenticated peers by req.federationPeer.nodeId; application-key traffic without a user identity falls back to source IP.

When REDIS_URL is configured, request counters and concurrent-stream reservations use Redis and are shared across instances. In a multi-instance deployment, set RATE_LIMIT_REDIS_REQUIRED=true so the service refuses to start without the shared store. Without Redis, counters and stream slots are process-local and suitable only for a documented single-instance deployment.

backend/middleware/chatRateLimit.js is intended to be mounted after chatAuth. backend/middleware/streamConcurrency.js provides a five-stream-per-account reservation. The authenticated-stream PR should wire the stream route in this order:

1. chatAuth
2. chatRateLimit(60)
3. createConcurrentStreamLimit({ maximum: 5 })
4. conversationStreams.open

The concurrency middleware releases a reservation on response close/finish and Redis reservations expire to recover from process crashes.

## Temporary fail-closed behavior and merge order

Until the owner-checked chat changes are deployed:

- /events and /stream/:conversationId return 410 instead of exposing the legacy unauthenticated feed.
- /uploads serves attachments only after independent account authentication, request throttling and attachment-owner authorization; shared browser keys alone grant no download access.

This branch carries the owner-checked attachment path from #191; retain it when integrating subsequent chat changes. After #192 is rebased and approved, replace the temporary stream 410 with the ordered authenticated handler above. Do not restore the old handlers before those protections are present.

No upload-creation endpoint exists in the current main tree; when one is introduced, place upload throttling on that actual write operation, not only on static download paths.

## CORS configuration

Set CORS_ALLOWED_ORIGINS to the exact deployed chat UI/application origins (comma-separated). Do not use * with credentials. The default remains the existing NTARI web origin. Authorization and the required integration/federation headers are explicitly allowed for preflight.
