# Retry-safe message sending

## Why this exists

A client can lose its connection after the backend has saved a message but
before it receives the response. Sending the same request again previously
created another message, repeated its broadcasts, and could generate another
AI reply. A unique message ID generated by the server cannot identify that retry.

`POST /messages/:conversationId` now accepts an optional `Idempotency-Key` header.
The client creates a fresh key for each deliberate send and keeps that same key
and payload for every retry of that send. A UUID is suitable. This backend change
does not add automatic retries or change any frontend; clients must opt in.

```http
POST /messages/conversation-123
Authorization: Bearer <token>
Idempotency-Key: 573d9ba2-9d86-4da2-b752-12b085b838d1
Content-Type: application/json

{"from":"user","to":"ai","content":"When should I plant tomatoes?","type":"text"}
```

The existing `{message, ai?, reply?}` success shape and `201` status are preserved.
A completed retry returns the same persisted message and reply, including their
IDs and timestamps, without uploads, broadcasts, token streaming, or AI calls.
Clients that consume both HTTP and SSE should reconcile using message IDs.

## Contract

Keys contain 1–128 printable ASCII characters, without spaces. Scope is the
conversation plus the authenticated JWT `userId`, or the accepted API credential.
It is never the caller-supplied `from` label. All clients sharing an API credential
share its retry namespace; key uniqueness is their responsibility. JWT refreshes
keep the same namespace when `userId` is unchanged; rotating an API key changes it.
The middleware's existing authentication and conversation-access behavior is
unchanged. Retry scoping does not add participant authorization to conversations.

The payload fingerprint covers `from`, `to`, `content`, `type` (default `text`),
and an attachment's name, MIME type, and base64 data. JSON property order does not
matter. Fields ignored by the existing send path do not distinguish requests.

| Status | Code | Meaning and client action |
| --- | --- | --- |
| `201` | — | Original send completed, or its completed response was reconstructed. |
| `400` | `invalid_idempotency_key` | Fix the header before sending. |
| `400` | `idempotency_identity_required` | Keyed sends require a stable authenticated user ID or API key. |
| `409` | `idempotency_key_conflict` | Same key and scope, different payload. Do not overwrite the original send. |
| `409` | `message_send_pending` | Another request is running, or a worker stopped before recording the outcome. Retry the same key later; inspect the conversation if it remains pending. |
| `410` | `message_send_removed` | The original message or reply was deleted. A retry will not recreate it. |
| `500` | `message_send_failed` | Delivery failed after claiming the key. This failure is retained; repeating the key does not rerun side effects. Inspect the conversation. |
| `503` | `message_send_unavailable` | Receipt storage could not acknowledge a claim. This request did not start delivery. Retry only with the same key; the write may have committed despite a lost acknowledgment. |
| `503` | `message_send_uncertain` | Delivery ran, but recording its outcome failed or timed out. Retry only with the same key and inspect the conversation; do not automatically use a new key. |

Authentication errors retain their existing responses. A database read failure
while reconstructing a completed response uses the existing generic `500` path;
the receipt remains completed, so retrying the same key does not rerun delivery.

## How the guard works, and its limits

A conditional DynamoDB put claims a receipt before any message or upload is
written. Competing workers read that receipt consistently. Only the successful
claimant invokes the existing delivery function. A conditional update records
completion or terminal failure; completed success receipts point to persisted
messages, not copies of their text.

This is not an exactly-once transaction across DynamoDB, local files, SSE, and
an external AI provider. A crash after claiming the key can leave a permanent
pending receipt, including when no message was written. There is deliberately no
lease takeover or automatic reset: replaying an uncertain operation could create
the duplicates this feature prevents. Pending sends require operator inspection
of stored messages and provider activity. No recovery endpoint is added here.
The existing AI responder's fallback behavior is unchanged.

Receipts have no automatic expiry. Deleting or expiring them, dropping their
table, or restoring it out of step with Messages removes protection against old
retries. Retain and back up both tables together. Do not automatically clear a
receipt to unblock a client or instruct the client to generate a new key without
first reconciling any messages, uploads, and external work already produced.

## Provisioning

Before enabling keyed sends in a client, create a separate table. No existing
Messages key schema is changed. `MESSAGE_SEND_TABLE_NAME` defaults to `MessageSends`.

```sh
aws dynamodb create-table \
  --table-name MessageSends \
  --attribute-definitions AttributeName=id,AttributeType=S \
  --key-schema AttributeName=id,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST
```

Use the backend's configured AWS region and environment; provision through the
deployment's normal review process. Grant the backend `GetItem`, `PutItem`, and
`UpdateItem` on this table, and `GetItem` on Messages for response reconstruction.
The receipt table requires no GSI or TTL. Missing table/permission errors stop
keyed sends before delivery; requests without a header do not access this table.

Receipts contain only an opaque scoped-key hash, a payload hash, processing state,
and outcome references/status. They contain no raw keys, credentials, account
profiles, attachment bytes, or chat narrative. Keep this application metadata
private to the platform, alongside its message store. Conversation deletion still
erases its message content; retained receipts prevent resurrection on retry.

API-credential receipt IDs use asynchronous scrypt (`N=16384`, `r=8`, `p=5`,
32-byte output). The salt is the hex SHA-256 of the JSON array
`["message-send-api-key-v2", conversationId, idempotencyKey]`; credential bytes
never enter a fast hash. This makes offline credential guesses against leaked
receipts expensive. Each active derivation uses roughly 16 MiB; concurrent work
runs through Node's worker pool. JWT receipt IDs and payload fingerprints retain
SHA-256 because they do not include authentication secrets.

This replaces the undeployed API-key ID derivation from the initial PR revision.
Disposable test receipts from that revision cannot replay under this derivation.
Do not mix the two revisions' API-key workers or reuse old test receipts as
production retry protection.

## NTARI boundaries

This extends the existing application message API. It does not edit a sealed
dialog, append narrative to the commons, change assessment distributions, or
alter escrow, balances, or governance. Existing `CONFORMANCE.md` in-review labels
remain in review. The new receipt state is operational application metadata, not
the append-only JFA exchange record, and is not federated or exported here.

## Verification

`npm test` includes HTTP tests using the real auth, controller, persistence, and
streaming code, with only DynamoDB and the external AI provider replaced.

The separate integration check uses the real SDK and DynamoDB Local, two HTTP
worker processes, restart/replay, and process death during an AI call. It creates
and deletes uniquely named tables, refuses non-loopback endpoints, and uses a
local AI fixture without contacting an external provider:

```sh
docker run --rm -d --name agrinet-retry-check \
  -p 127.0.0.1:18001:8000 amazon/dynamodb-local:latest \
  -jar DynamoDBLocal.jar -inMemory -sharedDb
DYNAMODB_TEST_ENDPOINT=http://127.0.0.1:18001 node scripts/check-message-retries.js
DYNAMODB_TEST_ENDPOINT=http://127.0.0.1:18001 node scripts/check-message-retries.js --api-key
docker stop agrinet-retry-check
```
